# Design a feature

Read the request, available starter-pack requirements, and relevant existing code. For this one-day assignment, choose the smallest complete user flow that demonstrates the requested behavior.

- Identify the user's action, observable result, and acceptance cases, including the meaningful failure path. For UI work, describe the screen states and how the user moves between them.
- Define only the data, state transitions, and interfaces needed for this feature. Use existing conventions; if no stack exists, justify the minimal choice against the assignment and available runtime before introducing dependencies.
- When evidence or approval is involved, consult `../evidence-review/SKILL.md` to check the proposed state flow. Separate starter-pack requirements from implementation choices.
- State the chosen approach, a material alternative if one exists, and the tradeoff. Map each acceptance case to an observable check that implementation can run.

Deliver a short design in the conversation. Save a concise decision in README.md only when it is needed to reproduce or understand the implementation. Do not generate empty plans or require a separate approval round when implementation is already authorized.

Check the design against the actual task: every proposed component must serve an acceptance case, the scope must fit one developer's working day, and unresolved facts must be explicit. A design-only request ends with the design.
